### Exact Root Cause

**Auth.js v5 PKCE cookie host mismatch behind Vercel's reverse proxy.**

The PKCE flow works like this:
1. `/api/auth/signin/google` → Auth.js sets a `__Secure-next-auth.pkce.code_verifier` cookie scoped to the **perceived host**
2. Google redirects → `/api/auth/callback/google` → Auth.js reads that cookie to verify the exchange

On Vercel, requests arrive through a CDN/proxy layer. The actual client sends to `snapcart-two-gamma.vercel.app`, but the request header that reaches your function shows a different internal host unless `X-Forwarded-Host` is trusted. Without `trustHost: true`, Auth.js v5 refuses to trust that header and perceives a different host on the callback than on the signin — the cookie scoping doesn't match → **"Invalid code verifier"**.

### What I read in the actual installed source

**`@auth/core/lib/utils/cookie.js`** — the PKCE cookie name:
```js
pkceCodeVerifier: {
  name: `${cookiePrefix}authjs.pkce.code_verifier`,
  // cookiePrefix = useSecureCookies ? "__Secure-" : ""
}
```

**`@auth/core/lib/actions/callback/oauth/checks.js`** — the PKCE cookie is JWT-**encrypted**, not stored raw:
```js
const encoded = await encode({
  ...options.jwt,
  maxAge: COOKIE_TTL,
  token: { value: payload },
  salt: cookie.name,   // ← cookie NAME is the JWT decryption salt
})
```

**`@auth/core/lib/init.js`** — how `useSecureCookies` is determined:
```js
cookie.defaultCookies(config.useSecureCookies ?? url.protocol === "https:")
```

The `url` comes from `createActionURL` which reads `x-forwarded-proto` from headers. This is **request-specific and can vary** across Vercel function invocations.

---

### The exact failure chain

| Step | Request | `url.protocol` detected | `useSecureCookies` | Cookie name used as JWT salt |
|------|---------|------------------------|-------------------|------------------------------|
| 1 | `/api/auth/signin/google` | `https:` ✅ | `true` | `__Secure-authjs.pkce.code_verifier` |
| 2 | `/api/auth/callback/google` | `http:` ❌ (internal hop) | `false` | `authjs.pkce.code_verifier` |

Cookie name differs → JWT decryption salt differs → decrypt fails → `InvalidCheck` → Google gets wrong `code_verifier` → **`invalid_grant: Invalid code verifier`**

---

```ts
// src/auth.ts
NextAuth({
  trustHost: true,         // trust x-forwarded-host
  useSecureCookies: true,  // ← pins cookie name permanently
  ...
})
```

`useSecureCookies: true` hard-codes the cookie name to `__Secure-authjs.pkce.code_verifier` on **every single request**, eliminating the protocol-detection race condition entirely.

**Exact sequence of events per click:**

| Order | Event | What happens |
|-------|-------|-------------|
| 1 | `onClick` on `<div>` | `signIn("google")` → POST `/api/auth/signin/google` → PKCE cookie **#1** set with `code_challenge_A` sent to Google |

| 3 | Browser redirected to Google | Google received `code_challenge_A` (from request #1) |
| 4 | User picks account, Google redirects back | Browser sends cookie **#2** (new verifier, doesn't match `challenge_A`) |
| 5 | Auth.js sends `code_verifier` from cookie **#2** to Google | Google: `invalid_grant: Invalid code verifier` → `AccessDenied` |

```tsx
<motion.form onSubmit={handleLogin}>

  <button>Login</button>
</motion.form>

{/* ✅ Outside form — click only fires onClick, not onSubmit */}
<div onClick={handleGoogleSignIn}>
  Continue with Google
</div>
```
